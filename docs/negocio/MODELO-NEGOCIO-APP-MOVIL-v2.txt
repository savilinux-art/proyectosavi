2.2 Extensión necesaria de evidencias_entrega (migración mínima)

  Schema::table('evidencias_entrega', function (Blueprint $t) {
      $t->enum('tipo', ['firma_cliente','pdf_cliente_firmado','foto_entrega'])
        ->default('firma_cliente')->after('archivo_tamano');
      $t->enum('estado', ['vigente','invalidada_por_edicion'])
        ->default('vigente')->after('tipo');
      $t->timestamp('invalidada_at')->nullable()->after('estado');
      $t->string('invalidada_por', 255)->nullable();
      $t->text('invalidada_motivo')->nullable();
      $t->index(['salida_id', 'estado']);
  });

3.11 🚨 Offline + ubicación: promesas honestas

  Lo que SÍ funciona offline:
    - GPS del teléfono (primer fix puede tardar)
    - lat/lng/timestamp → SQLite local
    - Foto → SQLite local
    - Envío al sync cuando hay red

  Lo que NO funciona offline:
    - Traccar (no recibe sin red, ya era sabido)
    - Reverse geocoding (calle desde lat/lng) — NO usar offline
    - Validar contra geocerca — F2

  Riesgos operativos aceptados:
    - GPS no fija en interiores → timeout 15s → permitir con
      fuente='no_disponible' y flag pendiente_revision
    - Mock location → fuente='mock' + alerta al sync
    - Hora desviada → capturado_at (dispositivo, confiable)
                      + created_at (servidor, autoritativo)
    - Batería → GPS solo en inicio/fin/foto, no continuo

       → evento 'pausada' + foto opcional tipo='proceso'

       → evento 'reanudada' + foto opcional tipo='proceso'

  POST /api/instalaciones/{id}/finalizar
       → fecha_hora_fin := capturado_at
       → estatus := ⏳ (ver Q3.4)
       → evento 'finalizada' + foto tipo='fin' obligatoria
       → payload: capturado_at, lat/lng/precision/fuente

  POST /api/instalaciones/{id}/fotos (multipart, batch 1..N)
       → tipo ∈ inicio|proceso|fin|incidencia
       → lat/lng/precision/fuente opcional por foto
       → guarda en instalacion_fotos

  POST /api/instalaciones/{id}/checklist
       → check_list (JSON libre F1)
       → evento 'checklist_actualizado'

  POST /api/instalaciones/{id}/eventos
       → tipo ∈ incidencia|nota_agregada
       → payload_json libre
       → evento correspondiente

  Regla del servidor para capturado_at:
    - si capturado_at > now() + 5 min  → rechazar (reloj desviado)
    - si capturado_at < now() - 30 días → aceptar + flag pendiente_revision

§7. FLUJOS POR ROL
================================================================================

  7.1 Almacenista (web)
    - Crea salida, imprime PDF, entrega material al técnico.
    - Verifica salidas pendientes de firma en el sistema.

  7.2 Técnico (móvil)
    - Login inicial con red (Sanctum, token 30 días).
    - Pull inicial: catálogos + salidas + instalaciones asignadas.

    Ciclo Entrega (Módulo A):
      a. Lleva material + papel al cliente.
      b. Cliente firma.
      c. Fotografía el papel.
      d. Sube cuando hay red.

    Ciclo Instalación (Módulo B):
      a. Abre instalación asignada.
      b. Pulsa "Iniciar" (offline) → foto inicio + lat/lng.
      c. Durante el día: fotos de proceso/incidencia con ubicación.
      d. Pulsa "Pausar" si se va, "Reanudar" al volver.
      e. Pulsa "Finalizar" → foto fin + lat/lng.

§13. LECCIONES DE ESTA SESIÓN
================================================================================

  1. El dump es la fuente de verdad, no el resumen. El resumen v2.4.0
     decía "drop id_usuario_asignado hecho" — el dump lo desmintió.
     Regla: antes de diseñar sobre un campo, verificar en dump.

  2. Reusar > crear. Dos tablas del v1 (salida_archivos, instalacion_
     evidencias) ya existían con otro nombre. Antes de proponer nueva
     tabla, buscar en dump por nombre aproximado y por columnas.

  3. La semántica de las columnas es tan importante como el tipo.
     fecha_hora_inicio NULL/valor era ambiguo. Confirmar con el usuario
     qué significa cada fecha antes de escribir migraciones.

  4. Traccar + App no son excluyentes. Traccar = trayecto continuo;
     App = hitos con timestamp. Convivencia limpia, no reemplazo.

  5. Offline es un compromiso. No todo lo que hay online funciona
     offline (geocoding, validación contra geocerca). Documentar
     los límites explícitamente para no prometer lo que no se cumple.

  6. El flujo Telegram ya resuelve el problema de negocio. La app
     móvil reimplementa lo mismo, offline. Paridad funcional primero,
     mejoras después.
