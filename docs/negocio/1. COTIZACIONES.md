## §1. Modelo conceptual confirmado

Venta ───── 1:1 ───── Proyecto (nacen juntos, mismo nombre_proyecto)
│
└── Cotización (v1, v2, v3...) 1:N hacia Proyecto
└── cotizacion_detalles (cabecera + detalle)
text


**Reglas del modelo:**

1. **1 venta = 1 proyecto.** Nacen juntos en el mismo request. `proyectos.nombre_proyecto`
   se copia de `ventas.nombre_proyecto`.
2. **Las cotizaciones se ligan al proyecto, NO a la venta.** No existe `cotizaciones.venta_id`.
   FK real: `cotizaciones.proyecto_id → proyectos.id`.
3. **N cotizaciones = 1 proyecto.** Cada versión es una fila nueva con folio propio.
   No hay jerarquía padre-hijo entre versiones.
4. **Corrección a Q-48:** la frase correcta es "1 venta = 1 proyecto; N cotizaciones = 1 proyecto".
   NO es "N ventas = 1 proyecto".
5. **Borrado:** una venta/proyecto sin cotizaciones se puede borrar; con cotizaciones,
   NO (se necesita histórico). ⚠️ La BD actual contradice esto (ver §7).

§3. Ciclo de vida de la cotización
3.1 Estados (enum real)
Estado	Significado	Uso hoy
borrador	En construcción, no enviada	✅ Operativo
enviada	Ya se envió al cliente, esperando respuesta	✅ Operativo
aprobada	El cliente ya la aceptó → dispara reserva	✅ Operativo
rechazada	Cliente dijo no	✅ Operativo
facturada	Declarada en enum, reservada para módulo futuro	❌ No se usa hoy

NO existe estado vencida automático. fecha_validez es informativo.
3.2 Transiciones
text

borrador ──enviar──► enviada ──cliente aprueba──► aprobada ──facturar──► facturada
   │                    │                            │
   │                    └──cliente rechaza──► rechazada (archivada)
   │
   └──editar (solo Admin si ya enviada)

aprobada ──liberar apartado──► aprobada + flag apartado_liberado=true  ⚠️ flag no existe aún

3.3 Permisos
Acción	 Admin	Ventas	Otros roles
Crear cotización	✅	✅	❌
Enviar al cliente (borrador → enviada)	✅	✅	❌
Marcar aprobada	✅	✅	❌
Marcar rechazada	✅	✅	❌
Modificar contenido en borrador	✅	✅	❌
Modificar contenido ya enviada	✅	❌	❌
Liberar apartado	✅	✅ (❓)	❌

Contradicción resuelta: marcar estatus ≠ editar contenido. Son operaciones distintas.
§4. Líneas de cotización
4.1 Tipos reales (3 en la práctica)
Tipo	inventario_id	Uso
Artículo catalogado	NOT NULL	Del inventario, con snapshot de precio
Artículo especial	NULL	Manual, no está en catálogo
Mano de obra	NULL	Siempre cantidad=1, varía precio

⚠️ Q-90: el schema no distingue "artículo especial" de "mano de obra" (ambos son inventario_id = NULL). Hace falta columna tipo.
4.2 Reglas de líneas

    Descripción: snapshot al cotizar. No se actualiza si cambia el inventario (Q-91 cerrado).

    Cantidad: entero (int(11)). No hay decimales.

    Descuento por línea: NO existe.

    Agrupación por sección: NO existe.

    Mano de obra: siempre cantidad = 1, varía precio_unitario. No se desglosa por técnicos/horas.

§5. Precios, monedas, impuestos
Aspecto	Regla
Moneda	Se elige al cotizar (MXN o USD según cliente/proyecto)
Tipo de cambio	NO se maneja. La cotización es moneda pura
Multi-moneda mismo proyecto	Permitido. v1 puede ser USD, v2 en MXN
IVA	Siempre 16%. Sin exenciones ni tasas frontera
Anticipo	Siempre 80% fijo. Hoy va como texto en condiciones
Descuentos globales	NO existen
Redondeo	2 decimales (decimal(12,2))

Fórmulas:
text

subtotal = Σ(importe) donde importe = cantidad × precio_unitario
iva      = subtotal × 0.16
total    = subtotal + iva

§6. Deuda técnica detectada
6.1 String FK a usuarios (agregar a §4.1 del doc de inventario)

cotizaciones.creado_por es varchar(255) FK a usuarios.usuario. Esto lleva la lista
de columnas string FK de 10 → 11.
6.2 Falta columna tipo en detalles

Hoy inventario_id IS NULL significa "mano de obra" o "artículo especial" o "línea libre".
Indistinguibles. → Q-90.
6.3 Falta flag apartado_liberado

La regla de negocio dice que liberar apartado deja la cotización en aprobada + flag.
El flag no existe en el schema. → Q-98.
6.4 Default de moneda incorrecto

DEFAULT 'USD' no refleja el negocio (debería ser MXN o sin default). → Q-88.
6.5 Sin plantilla de condiciones

El texto "** SE REQUIERE EL 80% DE ANTICIPO..." se copia-pega a mano. Candidato a plantilla. → Q-97.
§7. Conflictos schema ↔ negocio
7.1 CASCADE vs. histórico obligatorio

Schema: cotizaciones.proyecto_id ON DELETE CASCADE → borrar proyecto borra cotizaciones.
Negocio: si tiene cotizaciones, NO se puede borrar (histórico).

Resolución pendiente (Q-86): decidir cuál manda.

    Opción A: cambiar FK a RESTRICT (proteger histórico)

    Opción B: aceptar CASCADE y confiar en no borrar proyectos

    Opción C: soft-delete en proyectos

7.2 Borrar cliente cascadea cotizaciones

Mismo problema que 7.1 pero con cliente_id. Si se borra un cliente → se van sus cotizaciones.
7.3 Borrar usuario cascadea cotizaciones

Si se borra admin (u otro usuario que haya creado cotizaciones) → se van todas. Muy peligroso.

Riesgo: al llegar a COT-999999 → decidir padding o ampliar. Lejano pero anotado.
