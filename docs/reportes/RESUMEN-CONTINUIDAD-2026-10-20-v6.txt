## 3. HALLAZGOS CLAVE DE ESTA SESIÓN
--------------------------------------------------------------------------------

### 3.1 User vs Usuario (Regla 26 NUEVA)
El proyecto usa App\Models\Usuario, NO App\Models\User.
- El usuario autenticado se accede con $usuario->usuario (string PK)
- NO con $usuario->id ni $usuario->name
- Los `use App\Models\User;` en código nuevo son SIEMPRE sospechosos
- InstalacionFotoService fue creado con `?User $subidaPor` → TypeError
  en runtime, resuelto cambiando a `?Usuario $subidaPor`

### 3.2 $status colado dentro del array (Regla 25 NUEVA)
`response()->json([...], $status)` debe tener el `]` externo ANTES
de `, $status`. Un `$status` dentro del array es sintaxis válida en PHP
(clave numérica 0) y silencioso como bug: el status HTTP queda en 200.
Síntoma: assertCreated() falla con "Expected 201, got 200".
Solo visible con `awk '/private function respuesta/,/^    }$/'`, no con
grep de la firma (la firma SÍ tenía int $status = 200 correcto).

### 3.3 InstalacionFotoService — Opción B confirmada
Servicio en app/Services/InstalacionFotoService.php con métodos:
- guardar(Instalacion, UploadedFile, tipo, ?Usuario, ...): InstalacionFoto
- guardarBatch(Instalacion, array fotos, ...): array
- urlTemporal(InstalacionFoto, minutos=10): string
- eliminarBlob(InstalacionFoto): void
- assertArchivoValido(UploadedFile): void (protected, defensa en profundidad)
- almacenarEnDisk(...): string (protected)
Constantes: DISCO='local', MAX_KB=10240, MIMES=['image/jpeg','image/png']
Usa getMimeType() (detecta por contenido), NO getClientMimeType() (spoofable).
GuardarBatch envuelve en DB::transaction → atomicidad.

### 3.4 guardarFotoSiViene() legacy NO se toca
Los 4 endpoints (iniciar/pausar/reanudar/finalizar) usan
guardarFotoSiViene() (privado en InstalacionEventoController).
B-15 usa el servicio nuevo. Coexistencia temporal.
Deuda: unificar en F2 (anotado como Q-131-extendida).

### 3.5 B-13 (POST /api/instalaciones/{id}/fotos batch) NO hecho
Estaba en el PASO D del v5. Decisión: saltar porque NO bloquea Flutter
(es 🟡 importante-no-bloqueante según MODELO-NEGOCIO-v2 §6).

## 6. B-16 / B-17 — BLOQUEANTES DE SYNC (próximo bloque)
--------------------------------------------------------------------------------

### 6.1 Objetivo
B-16: POST /api/sync/push     (batch idempotente)
B-17: GET  /api/sync/pull     (delta por since)

Sin estos, Flutter "funciona" pero pierde datos offline al reinstalar.

### 6.2 Decisiones de arquitectura NO TOMADAS (resolver ANTES de codear)
🔴 D-1: ¿sync_log separada o uuid_cliente en cada tabla sincronizable?
        - Opción A: tabla sync_log (id, tabla, registro_id, uuid_cliente,
          operacion, payload_json, aplicado_at, resultado)
          Ventaja: una sola migración, historial completo, auditoría.
          Desventaja: búsqueda por uuid_cliente requiere índice y join.
        - Opción B: uuid_cliente en cada tabla (eventos, fotos, checklist,
          etc.) + UNIQUE por tabla.
          Ventaja: lookup directo, idempotencia natural.
          Desventaja: N migraciones, N índices, mantener en N modelos.
        VOTO PENDIENTE.

🔴 D-2: Resolución de conflictos exacta.
        El modelo de negocio dice "server-wins con log".
        ¿Server-wins por CAMPO o por REGISTRO?
        - Por registro: si server tiene versión más nueva, se descarta
          el push entero. Simple. Puede perder datos.
        - Por campo: solo campos modificados en server ganan. Complejo.
        VOTO PENDIENTE.

🔴 D-3: ¿Qué se sincroniza? (catálogo vs transaccional)
        Catálogo (pull-only): proyectos, clientes, categorias, inventario,
        estatus. Sin uuid_cliente. Sin push.
        Transaccional (push+pull): instalacion_eventos, instalacion_fotos,
        check_list. Con uuid_cliente.
        ¿evidencias_entrega (Módulo A) entra en B-16 o va en B-08 aparte?
        VOTO PENDIENTE.

🔴 D-4: Orden de operaciones dentro de un batch.
        Si el batch trae [evento, foto, checklist] y la foto referencia
        al evento:
        - ¿Se aplica en orden de llegada? (riesgo de FK antes que padre)
        - ¿Se ordena por tipo (padres antes que hijos)?
        - ¿Se rechaza el batch entero si una falla? (atomicidad)

🔴 D-5: Manejo de referencias huérfanas.
        Si el push incluye un evento para instalacion_id=42, pero la
        instalación 42 fue borrada o reasignada a otro técnico:
        - ¿Rechazar con 422? → la app debe reintentar sin fin
        - ¿Aceptar con flag pendiente_revision? → datos huérfanos
        - ¿Aceptar silenciosamente? → datos perdidos en limbo
        VOTO PENDIENTE.

🔴 D-6: Estructura del pull (delta).
        GET /api/sync/pull?since=<iso>
        Respuesta:
        - ¿Normalizada por tabla? {instalaciones: [...], eventos: [...], ...}
        - ¿Raw por updated_at? [{tabla, ...fila}, ...]
        - ¿Paginada? ¿Qué page_size máximo? ¿El cliente puede pedir
          page=2 y perder consistencia si alguien más escribió entre pag?
