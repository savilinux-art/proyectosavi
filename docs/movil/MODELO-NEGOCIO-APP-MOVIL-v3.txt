2.2 Extensión necesaria de evidencias_entrega (migración mínima)

  Schema::table('evidencias_entrega', function (Blueprint $t) {
      $t->enum('tipo', ['firma_cliente','pdf_cliente_firmado','foto_entrega'])
        ->default('firma_cliente')->after('archivo_tamano');
      $t->enum('estado', ['vigente','invalidada_por_edicion'])
        ->default('vigente')->after('tipo');
      $t->timestamp('invalidada_at')->nullable()->after('estado');
      $t->string('invalidada_por', 255)->nullable();
      $t->text('invalidada_motivo')->nullable();
      $t->index(['salida_id', 'estado']);
  });

  Un técnico puede:
    A) Hacer 1 instalación en 1 o varios días (Palomar 3 días)
    B) Hacer hasta 3 instalaciones en 1 día (Redes + Cámaras + Audio)
    C) Mezclar

  NO se crea tabla jornadas. El timeline vive en instalacion_eventos.

  🔄 NUEVO (v3): la jornada de trabajo puede transcurrir COMPLETA sin
  internet (§15.4). El outbox del cliente acumula eventos de toda la
  jornada. El sync drena el outbox cuando vuelve la red. Esto NO cambia
  el modelo de datos, pero sí las expectativas de tamaño de batch y la
  criticidad de la política de retry (§16 Q-137).

3.11 🚨 Offline + ubicación: promesas honestas

  Lo que SÍ funciona offline:
    - GPS del teléfono (primer fix puede tardar)
    - lat/lng/timestamp → SQLite local
    - Foto → SQLite local
    - Envío al sync cuando hay red (puede ser jornada completa)

  Lo que NO funciona offline:
    - Traccar (no recibe sin red)
    - Reverse geocoding (calle desde lat/lng) — NO usar offline
    - Validar contra geocerca — F2

  Riesgos operativos aceptados:
    - GPS no fija en interiores → timeout 15s → permitir con
      fuente='no_disponible' y flag pendiente_revision
    - Mock location → fuente='mock' + alerta al sync
    - Hora desviada → capturado_at (dispositivo, confiable)
                      + created_at (servidor, autoritativo)
    - Batería → GPS solo en inicio/fin/foto, no continuo

3.12 🚨 Detección de discrepancias app vs Traccar (F2, B-18)

  Al sincronizar, si hay posición de Traccar en ventana ±5 min:
    - < 50m   → ok
    - 50-200m → precision_baja
    - > 200m  → discrepancia (NO rechazar, marcar para admin)

§7. FLUJOS POR ROL
================================================================================

  7.1 Almacenista (web)
    - Crea salida, imprime PDF, entrega material al técnico.
    - Verifica salidas pendientes de firma.

  7.2 Técnico (móvil)
    - Login inicial con red (Sanctum, token 30 días).
    - Pull inicial: catálogos + salidas + instalaciones asignadas.

    Ciclo Entrega (Módulo A):
      a. Lleva material + papel al cliente.
      b. Cliente firma (físico).
      c. Fotografía el papel.
      d. Sube cuando hay red.
      ✅ Técnico NO entrega al cliente, solo recaba evidencia.

    Ciclo Instalación (Módulo B):
      a. Abre instalación asignada.
      b. Pulsa "Iniciar" (offline) → foto inicio + lat/lng.
      c. Durante el día: fotos de proceso/incidencia con ubicación.
      d. Pulsa "Pausar" si se va, "Reanudar" al volver.
      e. Pulsa "Finalizar" → foto fin + lat/lng.
         → estatus := 'pruebas' (NO 'entrega')
      f. Todo se sincroniza al recuperar red (puede ser jornada completa).

    Ve estado de sync de cada elemento.

  7.3 Cliente

§13. LECCIONES DE LA SESIÓN v3
================================================================================

  1. Preguntar "¿quién hace X?" antes de asumir. La v2 votaba 'entrega'
     al finalizar sin saber que el técnico NUNCA entrega al cliente.
     La consecuencia era un enum incorrecto en el side effect del sync.

  2. El propósito guía el diseño. Cuando el usuario dijo "evidencias para
     histórico", cambió todo: check_list no descarta updates, eventos son
     inmutables, FK RESTRICT en vez de CASCADE, sync_log solo guarda
     problemas (los eventos son el log completo).

  3. La regla de negocio se refleja en el esquema. "Nunca se borra una
     instalación iniciada" = FK RESTRICT. No hace falta SoftDeletes
     (que bloquearía también las no iniciadas). El esquema debe expresar
     la regla exacta, no una aproximación.

  4. Offline de jornada completa ≠ offline de minutos. Cambia:
     tamaño del batch, frecuencia de reintentos, criticidad de retry
     policy, ventana de huérfanos. El diseño lo tolera (batch atómico,
     orden por capturado_at), pero las pruebas de carga deben ser
     realistas.

  5. Las decisiones de arquitectura se cierran con trade-offs explícitos,
     no con votos. D-1..D-6 tienen cada una su "por qué" documentado en
     §14. Si en F2 alguien quiere cambiar una, sabe qué se ganó y qué
     se perdió.

§14. SYNC — DECISIONES CERRADAS D-1 a D-6
================================================================================

14.1 D-1: Híbrido — uuid_cliente UNIQUE + sync_log dual

  Almacenamiento de idempotencia:

  ┌──────────────────┬──────────────────────────────────────────────────┐
  │ Tabla            │ Estrategia                                       │
  ├──────────────────┼──────────────────────────────────────────────────┤
  │ instalacion_     │ uuid_cliente CHAR(36) UNIQUE en la tabla.        │
  │ eventos          │ El INSERT es el chequeo.                         │
  │ instalacion_     │ uuid_cliente CHAR(36) UNIQUE en la tabla.        │
  │ fotos            │ El INSERT es el chequeo.                         │
  │ check_list       │ sync_log UNIQUE (tabla, uuid_cliente).           │
  │                  │ Es columna JSON en instalaciones, no tabla.      │
  └──────────────────┴──────────────────────────────────────────────────┘

  Schema sync_log:

    CREATE TABLE sync_log (
      id              BIGINT UNSIGNED AUTO_INCREMENT PK,
      tabla           VARCHAR(50) NOT NULL,
      registro_id     BIGINT UNSIGNED NULL,
      uuid_cliente    CHAR(36) NOT NULL,
      operacion       VARCHAR(20) NOT NULL,   -- create|update
      payload_json    JSON NOT NULL,
      resultado       VARCHAR(20) NOT NULL,   -- ver §14.1.1
      detalle         TEXT NULL,
      intentado_at    TIMESTAMP NOT NULL,
      aplicado_at     TIMESTAMP NULL,
      created_at, updated_at,
      UNIQUE KEY uq_sync_log_tabla_uuid (tabla, uuid_cliente),
      INDEX idx_sync_log_resultado_fecha (resultado, intentado_at),
      INDEX idx_sync_log_registro (registro_id)
    );

  14.1.1 Valores permitidos de resultado:

    - 'ok'                  — se aplicó correctamente (SOLO check_list
                              lo persiste en sync_log; eventos/fotos
                              usan uuid_cliente UNIQUE en su tabla)
    - 'conflicto'           — server-wins por registro (§14.2)
    - 'huerfano'            — instalación no existe (§14.5)
    - 'error'               — fallo no-recuperable (validación, FK, etc.)
    - 'duplicado_distinto'  — mismo uuid_cliente, payload DIFERENTE
                              al registrado antes. Se detecta con hash
                              sha1 del payload canónico (JSON ordenado).
                              Se responde 409 al cliente.

  Rol dual de sync_log:
    - eventos/fotos: solo guarda no-ok
                     (conflicto, huerfano, error, duplicado_distinto)
    - check_list:    guarda TODAS las ops
                     (es su único lugar para el UUID)

14.2 D-2: Server-wins por REGISTRO — aplica SOLO a check_list

  Eventos y fotos son append-only:
    - No hay update sobre instalacion_eventos (los cambios de estado
      crean eventos NUEVOS, no mutan anteriores).
    - No hay update sobre instalacion_fotos (se sube otra foto, no se
      edita).
    - Sin conflicto posible → solo idempotencia (D-1).

  check_list:
    - Es columna JSON en instalaciones.
    - Si instalaciones.updated_at > push.timestamp:
        rechazar el update
        registrar sync_log.resultado='conflicto'
        responder 409 al cliente con el estado actual del servidor
    - Si es la primera actualización tras el pull inicial:
        aplicar sin conflicto

14.3 D-3: Alcance transaccional (3 tablas)

  Catálogo (pull-only):       proyectos, clientes, categorias,
                              inventario, estatus, salidas, salida_detalle,
                              evidencias_entrega
  Transaccional (push+pull):  instalacion_eventos, instalacion_fotos,
                              check_list
  Fuera de B-16:              evidencias_entrega
                              (Módulo A, tiene su propio endpoint
                               multipart y su propio servicio en F2)

  Técnico NO descuenta inventario (es trabajo del almacenista).
  Técnico NO acepta/rechaza salidas desde la app (proceso físico).

14.4 D-4: Orden, atomicidad y side effects

  - Reordenar batch por capturado_at ASC (no por orden de llegada).
    Razón: si el retry reordena y llega finalizada antes que iniciada,
    el side effect escribiría fecha_hora_fin antes de fecha_hora_inicio.

  - Batch atómico (DB::transaction):
    - Fallo no-recuperable → rollback total → 422 con detalle por op.
    - Idempotentes (mismo uuid) → skip silencioso, batch continúa.

  - Side effects (X en F1, Y en F2):

      iniciada   → fecha_hora_inicio := capturado_at (si era NULL)
                   estatus := 'en_proceso'
      pausada    → (no toca instalaciones)
      reanudada  → (no toca instalaciones)
      finalizada → fecha_hora_fin := capturado_at
                   estatus := 'pruebas'  ← Q3.4 cerrado (§3.4)
      incidencia → (no toca instalaciones)
      nota_agregada → (no toca instalaciones)
      checklist_actualizado → ver §14.4.1

  14.4.1 check_list — cada update crea evento + solo el último
         actualiza la columna:

    Dentro de un batch con N updates de check_list para la misma
    instalación:
      1. Insertar N eventos en instalacion_eventos
         (tipo='checklist_actualizado', payload completo)
      2. Ordenar por capturado_at ASC
      3. Actualizar instalaciones.check_list SOLO con el de
         capturado_at más reciente

    Ningún update se "descarta": todos quedan como evento (histórico).
    Solo el más reciente aplica al caché (columna).

  14.4.2 Service compartido (interpretación 3):

    La lógica de iniciar/pausar/reanudar/finalizar/checklist/eventos
    vive en un Service (patrón InstalacionFotoService de B-15).
    Los endpoints HTTP y el sync push AMBOS llaman al Service.
    NO se duplica lógica. NO se hace replay interno de HTTP.

14.5 D-5: Huérfanos y borrado

  1. Huérfanos (instalación_id no existe al aplicar push):
     - Aceptar con sync_log.resultado='huerfano' + payload completo.
     - Cliente recibe 200 (operación registrada, no reintenta).
     - Admin recupera manual desde web.
     - Frecuencia esperada: ~0 (regla §15.2 impide borrar instalaciones
       ya iniciadas; regla §15.1 impide reasignar técnicos).
     - Test mínimo: push a instalación inexistente no rompe ni pierde
       payload ni fuerza reintento del cliente.

  2. Borrado de instalaciones:
     - FK RESTRICT en instalacion_eventos.instalacion_id
     - FK RESTRICT en instalacion_fotos.instalacion_id
     - Sin SoftDeletes en Instalacion.
     - Regla de negocio: no se borra una instalación ya iniciada
       (con eventos o fotos). RESTRICT lo hace imposible por esquema.
     - Instalaciones no iniciadas sí se pueden borrar (no hay RESTRICT
       activa porque no tienen filas hijas).
     - Q-140 (F2): mensaje legible en el admin al intentar borrar.

14.6 D-6: Pull — estructura, paginación, since

  1. Estructura del response: NORMALIZADA POR TABLA
     {
       "since": "2026-10-20T14:30:00Z",
       "next_since": "2026-10-20T18:45:12Z",
       "instalaciones": [...],
       "instalacion_eventos": [...],
       "instalacion_fotos": [...],
       "check_list": [...],       // solo las filas con cambios
       "salidas": [...],
       "evidencias_entrega": [...],
       "catalogos": {
         "proyectos": [...],
         "clientes": [...],
         "categorias": [...],
         "inventario": [...],
         "estatus": [...]
       }
     }

  2. Paginación: SIN PAGINAR EN F1
     - Bootstrap completo ~2 MB en una request.
     - Deltas diarios mucho menores.
     - Migración a keyset en F2 si el catálogo crece (sin cambiar
       el contrato HTTP: el cliente acepta `cursor` opcional).

  3. `since` se compara contra `updated_at` UNIFORME en todas las tablas.
     - Incluso en instalacion_eventos, because updated_at mide
       "cuándo cambió en servidor", no cuándo fue capturado.
     - El cliente ordena por capturado_at localmente si lo necesita
       para el timeline.

  4. Formato de `since`: ISO 8601 UTC (2026-10-20T14:30:00Z).
     Sin ambigüedad de zona horaria.

  5. Filtros de scope:
     - instalaciones: EXISTS instalacion_instalador
                      WHERE instalador_usuario = :current_user
     - salidas: WHERE entregado_a = :current_user
     - instalacion_eventos, instalacion_fotos, check_list:
                WHERE instalacion_id IN (las anteriores)

§15. REGLAS DE NEGOCIO CONFIRMADAS (v3)
================================================================================

  15.1 Asignación de técnico es INMUTABLE

    Una vez asignado un técnico a una instalación, NO se puede reasignar
    a otro. Motivo: evitar conflictos entre técnicos sobre quién hizo qué.

    Consecuencias:
      - instalacion_instalador: mapping estable, el pull no cambia por
        reasignación.
      - Huérfanos por reasignación: imposibles.
      - Multi-técnico: coexiste (9 filas para 7 instalaciones), pero
        agregar técnico no es reasignar.

    ⏳ Q-138: confirmar si "quitar técnico antes de iniciar trabajo" es
    una corrección de error de asignación (permitida) o también prohibido.

  15.2 El admin NO cancela instalaciones — solo las PAUSA

    "Cancelar" no existe como transición. El admin pausa por impedimento.
    La instalación pausada sigue existiendo, sus eventos y fotos se
    aplican normalmente.

    ⏳ Q-139: ¿"pausar admin" == "pausar técnico" (mismo estatus) o son
    dos estatus distintos?

    Regla derivada: NUNCA se borra una instalación YA INICIADA. Se
    conserva para histórico. Solo se pueden borrar instalaciones sin
    eventos ni fotos. Se garantiza por FK RESTRICT (§14.5).

  15.3 Propósito de las evidencias: HISTÓRICO / AUDITORÍA

    Todas las evidencias del técnico (eventos, fotos, cambios de
    checklist) existen para crear un registro histórico que sirva
    como prueba en caso de disputas, auditorías o reclamos del cliente.

    Consecuencias de diseño:
      - instalacion_eventos: inmutable. Nunca se edita. Nunca se borra.
      - instalacion_fotos: inmutable. Si se "corrige", se sube otra y
        se marca vigente vs invalidada (patrón §2.2).
      - check_list: la columna es caché; el histórico vive en eventos
        checklist_actualizado.
      - FK RESTRICT: protege la evidencia ante borrados accidentales.
      - created_at (servidor) y capturado_at (dispositivo) se preservan
        ambos para auditoría forense.

    ⏳ Q-136: confirmar política de inmutabilidad para el admin en web
    (¿puede invalidar sin borrar? ¿o puede borrar?).

  15.4 Offline puede ser JORNADA COMPLETA

    Aunque el diseño conceptual es "offline para momentos sin red",
    operativamente una jornada completa puede transcurrir sin internet.
    El outbox del cliente acumula 20-50+ operaciones y se drena cuando
    vuelve la red.

    Consecuencias:
      - Batch atómico por jornada (DB::transaction).
      - Orden por capturado_at ASC crítico (retry puede reordenar).
      - Retry con backoff exponencial (Q-137).
      - Test E2E con batch de jornada completa (10+ eventos,
        5+ fotos, 5+ updates de check_list).

  15.5 El técnico NO entrega al cliente. El SUPERVISOR sí.

    El técnico recaba evidencias (fotos de proceso, inicio, fin,
    incidencias) y las sincroniza. La entrega formal al cliente la
    hace el SUPERVISOR desde web, tras verificar el trabajo.
    Eso cambia el estatus a 'entrega'.

    Consecuencia: el side effect de 'finalizada' deja estatus='pruebas'
    (§3.4).

  15.6 El técnico NO acepta/rechaza salidas desde la app

    El técnico revisa el material físicamente contra la salida de
    inventario. Si no coincide, NO acepta la salida — proceso físico,
    regla de empresa. No se automatiza.

    Consecuencia: salidas NO son transaccionales en el sync.
    evidencias_entrega (Módulo A) tiene su propio endpoint multipart.

  15.7 El técnico NO descuenta inventario

    El inventario lo maneja el almacenista. El técnico solo consulta.

    Consecuencia: movimientos_inventario NO es transaccional en el sync.
